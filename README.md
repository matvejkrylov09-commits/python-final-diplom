# Сервис автоматизации закупок

Учебный дипломный проект Нетологии: сервис закупок на Django REST Framework.
Реализованы модели, импорт YAML, API пользователей, каталога, корзины,
контактов, заказов и поставщика. Для сотрудников доступно изменение
статуса оформленного заказа через отдельный защищённый endpoint.

## Технологии

Python 3.12.10, Django, Django REST Framework, SQLite, PyYAML, requests, django-rest-passwordreset. Для разработки выбран консольный email backend.

## Установка зависимостей

Для запуска по этой инструкции используйте Windows, PowerShell и Python **3.12.10**.

Откройте терминал в корне проекта — каталоге с `manage.py` и
`requirements.txt`. Все команды PowerShell ниже выполняются из этого каталога,
независимо от того, где сохранён проект:

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Активация окружения не обязательна: команды ниже используют его Python напрямую.
В `requirements.txt` закреплены прямые зависимости; версии транзитивных
зависимостей разрешает pip.

## Миграции и создание пользователей

```powershell
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py createsuperuser
```

`createsuperuser` запросит email и пароль. Суперпользователь активен и имеет
доступ к защищённому endpoint изменения статуса заказа.

Публичная регистрация создаёт покупателя. Для начального создания поставщика
используйте Django shell:

```powershell
.\.venv\Scripts\python.exe manage.py shell
```

В открывшейся Python-консоли:

```python
from getpass import getpass
from backend.models import User

supplier = User.objects.create_user(
    email=input('Email поставщика: ').strip(),
    password=getpass('Пароль поставщика: '),
    type=User.Type.SHOP,
    is_active=True,
)
exit()
```

Значения вводятся локально; не записывайте их в исходники. Если поставщик
уже существует, повторное создание не нужно. Это техническая подготовка
учётной записи, а не публичный API назначения ролей.

## Импорт прайса

Команда использует существующего пользователя с ролью `shop`:

```powershell
$supplierEmail = Read-Host 'Email существующего поставщика'
.\.venv\Scripts\python.exe manage.py import_products data/shop1.yaml --email $supplierEmail
```

Команда не создаёт пользователей. Исходный `data/shop1.yaml` сохранён без
изменений из официального репозитория Нетологии.

Повторная загрузка обновляет предложения по магазину и внешнему ID.
Исчезнувшие предложения получают остаток 0. Цена позиции заказа хранится
отдельно от текущего прайса. Замена товара под внешним ID, уже связанным
с оформленным заказом, отклоняется. При любой ошибке загрузка откатывается.

В официальном файле один магазин, четыре категории и 14 предложений.
Для покупки у нескольких магазинов создайте отдельную учётную запись
для каждого поставщика и загрузите его прайс.

## Запуск сервера

```powershell
.\.venv\Scripts\python.exe manage.py runserver
```

Сервер доступен по `http://127.0.0.1:8000/`; каталог —
`http://127.0.0.1:8000/api/v1/products/`. Корневой `/` не является страницей API
и может возвращать HTTP 404. Останавливается сервер через Ctrl+C.

## Основные сценарии

1. Зарегистрируйте покупателя, возьмите токен подтверждения из консоли
   сервера, подтвердите email и войдите. Используйте полученный токен
   авторизации в дальнейших запросах.
2. Выберите предложения в каталоге, добавьте их в корзину и создайте
   контакт доставки. Оформите заказ с ID корзины и контакта, затем
   проверьте подтверждение в консоли и откройте заказ в истории.
3. Войдите под учётной записью поставщика, загрузите прайс, проверьте
   приём заказов и откройте список заказов со своими позициями.
4. Войдите под учётной записью сотрудника и измените статус заказа.

## API пользователей и каталога

Ниже описан контракт текущей реализации.
Все маршруты заканчиваются `/`. Тело запросов передаётся как JSON.

| Метод | Путь | Назначение и входные поля |
|---|---|---|
| POST | `/api/v1/user/register/` | Регистрация: `first_name`, `last_name`, `email`, `password` |
| POST | `/api/v1/user/register/confirm/` | Подтверждение email: `token` |
| POST | `/api/v1/user/login/` | Вход: `email`, `password` |
| POST | `/api/v1/user/logout/` | Удаление текущего токена авторизации |
| GET | `/api/v1/user/details/` | Только собственный профиль |
| POST | `/api/v1/user/password_reset/` | Запрос восстановления: `email` |
| POST | `/api/v1/user/password_reset/confirm/` | Новый пароль: `token`, `password` |
| GET | `/api/v1/shops/` | Публичный список магазинов |
| GET | `/api/v1/categories/` | Публичный список категорий |
| GET | `/api/v1/products/` | Публичный список предложений |
| GET | `/api/v1/products/<id>/` | Детали предложения по внутреннему ID |

Регистрация создаёт неактивного покупателя и возвращает HTTP 201.
Пароль проверяется валидаторами Django и хранится в хешированном виде.
Токен подтверждения находится только в письме, в JSON он не возвращается.
Подтверждение активирует пользователя и удаляет его токены подтверждения.
Неверный или использованный токен возвращает HTTP 400.

Вход возвращает `{"token": "<токен авторизации>"}`. При неверных данных или
неактивном пользователе возвращается HTTP 400. Профиль и выход требуют
заголовок `Authorization: Token <токен авторизации>`; без него — HTTP 401.
Выход возвращает HTTP 204. Профиль не принимает ID другого пользователя.

Пример входа; подставьте данные созданной и активированной учётной записи:

```http
POST /api/v1/user/login/
Content-Type: application/json

{"email": "buyer@example.com", "password": "<ваш пароль>"}
```

Токен из ответа передаётся заголовком `Authorization: Token <токен>`.
Примеры email и токенов в документации не являются рабочими учётными данными.

Восстановление пароля реализовано через `django-rest-passwordreset`.
Для существующего, неизвестного и неактивного email возвращается один ответ:
HTTP 200, `{"status": "OK"}`. Письмо получает только активный пользователь
с доступным паролем. Токен действует 24 часа и после смены пароля удаляется.
Неверный, просроченный или использованный токен возвращает HTTP 404.
После смены пароля прежний токен авторизации отзывается; требуется новый вход.
Библиотека ограничивает запросы восстановления: по умолчанию 3 в сутки с IP.

Письма регистрации и восстановления выводятся в консоль сервера. В письмах
указаны токен и маршрут для POST-запроса; интерфейс подтверждения не создавался.

Фильтры списка предложений можно сочетать:

- `search` — подстрока названия без учёта регистра, включая кириллицу;
- `category` — внутренний ID категории;
- `shop` — внутренний ID магазина.

Пример: `/api/v1/products/?search=iphone&category=1&shop=1`.
Неверный формат фильтра возвращает HTTP 400, отсутствие совпадений — `[]`.

Предложение содержит `id`, `name`, `description`, `category`, `shop`, `model`,
`price`, `price_rrc`, `quantity`, `parameters`. Категория содержит `id` и `name`,
магазин — `id`, `name`, `state`, характеристики — список объектов `name`/`value`.
Цены передаются строками с двумя знаками после точки. Списки возвращаются
без пагинации. Персональные данные владельцев магазинов не публикуются.
`description` — необязательное описание общего товара. В исходном YAML
описаний нет: импорт оставляет их пустыми, не придумывая текст.

## Корзина

Все операции требуют токен авторизованного покупателя. Для пользователя
с ролью `shop` возвращается HTTP 403, без авторизации — HTTP 401.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/basket/` | Просмотр корзины |
| POST | `/api/v1/basket/` | Добавление предложения |
| PUT | `/api/v1/basket/` | Замена количества позиции |
| DELETE | `/api/v1/basket/` | Удаление позиций |

Примеры JSON-запросов с заголовками `Content-Type: application/json`
и `Authorization: Token <токен авторизации>`:

Добавление двух единиц предложения с ID 1:

```http
POST /api/v1/basket/

{"product_info": 1, "quantity": 2}
```

Повторное добавление увеличивает количество в существующей позиции.
Предложения разных магазинов можно добавлять в одну корзину.

Установка количества 3 у позиции с ID 7:

```http
PUT /api/v1/basket/

{"id": 7, "quantity": 3}
```

Удаление нескольких позиций:

```http
DELETE /api/v1/basket/

{"ids": [7, 8]}
```

Все успешные операции возвращают HTTP 200 и актуальное содержимое корзины:

```json
{
  "id": 2,
  "items": [
    {
      "id": 7,
      "product_info": 1,
      "name": "Телефон",
      "shop": {"id": 1, "name": "Первый магазин", "state": true},
      "price": "29.95",
      "quantity": 2,
      "total": "59.90"
    }
  ],
  "total": "59.90"
}
```

При отсутствии корзины GET возвращает
`{"id": null, "items": [], "total": "0.00"}` и ничего не создаёт.
Корзина создаётся только при первом успешном добавлении. После удаления
всех позиций она сохраняется пустой. У покупателя может быть только одна
активная корзина; ограничение также установлено в базе данных.

Количество передаётся положительным целым числом JSON. При добавлении
и изменении проверяются остаток и статус приёма заказов магазина.
Нулевой остаток, превышение остатка и неверные данные возвращают HTTP 400.
Добавление не уменьшает остатки и не резервирует товар.

Суммы рассчитываются по текущим ценам предложений с точностью до копеек.
Изменение прайса отражается при следующем чтении корзины. API корзины
не изменяет оформленные заказы. Попытка изменить чужую или оформленную
позицию возвращает HTTP 400. При удалении списка с недоступной позицией
не удаляется ни одна из переданных позиций.

## Контакты доставки

Операции доступны авторизованному пользователю только для своих контактов.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/user/contacts/` | Список собственных контактов |
| POST | `/api/v1/user/contacts/` | Создание контакта |
| DELETE | `/api/v1/user/contacts/<id>/` | Удаление собственного контакта |

Пример создания адреса с теми же заголовками авторизации и JSON:

```http
POST /api/v1/user/contacts/

{
  "city": "Москва",
  "street": "Ленина",
  "house": "1",
  "structure": "2",
  "building": "3",
  "apartment": "4",
  "phone": "+79990000000"
}
```

Обязательны непустые `city`, `street` и `phone`. Остальные части адреса
необязательны. `structure` — корпус, `building` — строение, как в модели.
Владелец назначается сервером. ФИО и email хранятся в профиле пользователя,
в контакте они не дублируются. Отдельного поля отчества в текущей модели нет.

Создание возвращает HTTP 201 и контакт с ID; шестой адрес — HTTP 400.
Удаление возвращает HTTP 204, для чужого или отсутствующего контакта —
HTTP 404. Удаление адреса не удаляет связанные заказы, ссылка становится
пустой; снимок адреса оформленного заказа сохраняется.
Без авторизации операции возвращают HTTP 401.

## Заказы

Доступ требует заголовок `Authorization: Token <токен авторизации>`
и роль покупателя. Без авторизации возвращается HTTP 401,
для поставщика — HTTP 403.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/orders/` | Оформление своей корзины |
| GET | `/api/v1/orders/` | История собственных заказов |
| GET | `/api/v1/orders/<id>/` | Детали собственного заказа |

Пример оформления с заголовком `Content-Type: application/json`:

```http
POST /api/v1/orders/

{"basket": 2, "contact": 1}
```

В запросе передаются ID корзины и существующего контакта текущего покупателя.
Успех: HTTP 201, `{"id": 2}`. Корзина становится заказом со статусом `new`.
После этого следующее добавление товара создаёт новую активную корзину.

Оформление выполняется целиком в транзакции. Проверяются принадлежность,
наличие позиций, положительное количество, остатки и приём заказов магазинами.
Остатки уменьшаются условными SQL-обновлениями. Если одна позиция недоступна,
откатываются все списания, цены, адрес и изменение статуса.

Первое условное обновление `basket` → `new` исключает повторное оформление
и получает блокировку записи SQLite до чтения остатков. Защита не зависит
только от `select_for_update()`. При занятости SQLite возвращается HTTP 409;
запрос можно повторить позже. Повторное подтверждение уже сохранённого заказа,
чужая корзина или контакт, пустая корзина и недостаточный остаток дают HTTP 400.

Примеры просмотра:

```http
GET /api/v1/orders/
GET /api/v1/orders/2/
```

История возвращает список объектов с `id`, `dt`, `state`, `total`.
Корзины исключаются. Детали дополнительно содержат `items` и `delivery_address`.
Позиция включает `id`, `product_info`, `name`, `shop`, `price`, `quantity`,
`total`. Суммы и цены передаются строками с двумя знаками после точки.
Чужой, отсутствующий заказ или корзина по адресу деталей возвращают HTTP 404.
Статус меняется только через отдельный endpoint для сотрудников,
описанный ниже.

При оформлении текущая цена предложения копируется в `OrderItem.price`.
Исторические суммы рассчитываются только по сохранённым ценам.
В `Order.delivery_address` сохраняются город, улица, дом, корпус, строение,
квартира и телефон. Последующие изменения или удаление контакта не меняют
этот снимок. Миграция также сохраняет доступные адреса старых заказов;
адрес, удалённый до появления снимков, восстановить из базы невозможно.

## Письма о заказе

После успешного commit отправляются два независимых письма через
`transaction.on_commit()`:

- покупателю — номер, товары и магазины, количества, цены, итог и доставка;
- администраторам из `settings.ADMINS` — накладная с теми же сведениями
  и данными покупателя.

При откате письма не отправляются. Повторное подтверждение заказа не создаёт
новые уведомления. Для локальной разработки письма выводятся в консоль сервера.

По умолчанию `ADMINS` пуст: письмо покупателю отправляется, накладная
администратору пропускается. Для настройки одного получателя перед запуском
сервера задайте переменную окружения в PowerShell:

```powershell
$env:ADMIN_EMAIL = 'admin@example.com'
.\.venv\Scripts\python.exe manage.py runserver
```

`admin@example.com` — пример, замените его адресом получателя.
Настройки формируют `ADMINS` из `ADMIN_EMAIL`; реальные адреса не нужно
записывать в исходники. Консольный backend выводит письмо, но не доставляет
его во внешний почтовый ящик.

Ошибка отправки после commit записывается в журнал Django и не отменяет
сохранённый заказ. Второе письмо всё равно будет обработано. Автоматических
повторных попыток отправки и фоновых задач в проекте нет.

## API поставщика

Все запросы требуют `Authorization: Token <токен поставщика>` и роль `shop`.
Без авторизации возвращается HTTP 401, покупателю — HTTP 403.
Наличие `is_staff` не заменяет роль поставщика и не расширяет выборку магазина.

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/partner/update/` | Импорт содержимого YAML |
| GET | `/api/v1/partner/state/` | Состояние своего магазина |
| POST | `/api/v1/partner/state/` | Включение или отключение приёма заказов |
| GET | `/api/v1/partner/orders/` | Заказы с позициями своего магазина |

### Загрузка прайса

Endpoint принимает JSON с единственным полем `yaml`, содержащим текст прайса.
Пример PowerShell для загрузки исходного файла:

```powershell
$supplierToken = '<токен поставщика>'
$headers = @{ Authorization = "Token $supplierToken" }
$body = @{
    yaml = Get-Content -Raw -Encoding UTF8 data/shop1.yaml
} | ConvertTo-Json
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/api/v1/partner/update/' `
    -Method Post -Headers $headers -ContentType 'application/json; charset=utf-8' `
    -Body ([System.Text.Encoding]::UTF8.GetBytes($body))
```

Успех — HTTP 200. Ответ содержит `shop_id`, `categories`, `processed`,
`created`, `updated`, `zeroed`. Используется тот же сервис, что и в команде
`import_products`; сохраняются транзакционность и правила повторного импорта.

Владелец определяется по токену. Передача владельца или ID магазина
в JSON либо в корне YAML отклоняется. Название `shop` в YAML относится
к магазину текущего поставщика, даже если у другого магазина такое же имя.
Поля внешнего URL не поддерживаются, сетевых загрузок нет.
Неверный YAML и ошибки данных возвращают HTTP 400. При ошибке базы
возвращается общий HTTP 500, подробности пишутся только в журнал сервера.

### Приём заказов

```http
GET /api/v1/partner/state/
Authorization: Token <токен поставщика>
```

Ответ содержит `id`, `name`, `state` своего магазина. Для изменения:

```http
POST /api/v1/partner/state/
Authorization: Token <токен поставщика>
Content-Type: application/json

{"state": false}
```

Для включения передайте `true`. Допускаются только JSON boolean:
строки `"true"`/`"false"`, числа 0/1 и `null` возвращают HTTP 400.
Нельзя передавать ID магазина или пользователя. Изменение состояния
сразу учитывается корзиной и оформлением заказа.

Если магазин ещё не создан, `state` и `orders` возвращают HTTP 404
с предложением сначала загрузить прайс. Повторный импорт сохраняет
установленное состояние магазина.

### Заказы магазина

```http
GET /api/v1/partner/orders/
Authorization: Token <токен поставщика>
```

В список попадают только оформленные заказы с предложениями своего магазина.
Корзины и заказы других магазинов исключены. Для смешанного заказа
возвращаются только собственные позиции, цены и суммы. Поле `total`
содержит сумму этих позиций, а не всего заказа.

Поля ответа: `id`, `dt`, `state`, `total`, `items`, `delivery_address`,
`recipient`. В `recipient` доступны имя, фамилия и email покупателя;
телефон находится в снимке доставки. Другие поля профиля не раскрываются.
Цены берутся из `OrderItem.price`, адрес — из снимка заказа.
Изменять заказ через этот endpoint нельзя.

## Изменение статуса сотрудником

Маршрут: `PATCH /api/v1/orders/<id>/status/`.

```http
PATCH /api/v1/orders/2/status/
Authorization: Token <токен сотрудника>
Content-Type: application/json

{"status": "confirmed"}
```

Доступен только активному пользователю с `is_staff=True`. Обычным
покупателям и поставщикам возвращается HTTP 403, без авторизации — HTTP 401.
Успех: HTTP 200, например `{"id": 2, "status": "confirmed"}`.

Разрешены `new`, `confirmed`, `assembled`, `sent`, `delivered`, `canceled`.
Нельзя менять статус корзины или переводить заказ в `basket` — HTTP 400.
Неизвестный статус и любые дополнительные поля запроса также дают HTTP 400,
отсутствующий заказ — HTTP 404.

Меняется только статус. Цены, позиции, доставка и остатки сохраняются;
`canceled` не запускает автоматический возврат остатков. Установка того же
статуса повторно не сохраняет заказ и не создаёт побочных эффектов.
Письма об изменении статуса не отправляются. Интерфейс администрирования
и сложные правила переходов не реализованы. Доступ сотрудника к этому
endpoint не открывает чужие контакты через обычный API.

## Ограничения локального режима и соответствия

Проект предназначен для учебного локального запуска: SQLite, `DEBUG=True`,
стандартный сервер Django и консольный email backend. Письма видны в терминале,
но не доставляются на настоящие адреса. Готовность к production не заявляется.

`SECRET_KEY` читается из переменной окружения; значение по умолчанию подходит
только для разработки. Переменные задаются средствами ОС, файл `.env`
автоматически не читается. Локальная база, `.env` и `.venv` исключены из Git.

В официальных текстах есть расхождения: `service.md` говорит об одном телефоне,
а пример модели помещает телефон в каждую запись адреса. Текущая реализация
следует модели: до пяти контактов с телефонами; единственность телефона
не ограничивается. ФИО и email получателя берутся из профиля, отдельного
отчества нет. Это выбранная трактовка расхождений официальных материалов.

Экспорт, админка заказов/склада, уведомления о смене статусов, Celery
и Docker не входят в выполненную часть. Смена на `canceled` не возвращает
остатки: endpoint изменяет только статус, как описано выше.
